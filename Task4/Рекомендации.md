# Программное обеспечение

##1. Неверное разбиение на сервисы

Приоритет: Критический

Рекомендуемая мера: Провести проектирование по DDD перед началом разработки. Начать с пилотного сервиса, проверить границы на практике.

## 2. Отсутствие кеширования

Приоритет: Высокий

Рекомендуемая мера: Внедрить Redis для данных, не требующих сильной актуальности (расписание врачей, справочники). Настроить инвалидацию кэша.

## 3. Не оптимизированные запросы к БД

Приоритет: Средний

Рекомендуемая мера: Внедрить профилирование запросов (query profiling) и мониторинг медленных запросов в БД. Обязательный код-ревью для SQL-запросов




# Интеграция

## 1. Параллельная работа старой и новой систем во время перехода

Приоритет: Критический

Рекомендуемая мера: Разработать стратегию "двухфазной" миграции: сначала только чтение из новой системы, затем поэтапный перевод операций записи. Внедрить синхронизацию ключевых данных.

## 2. Сложность замены OLE на современные протоколы

Приоритет: Средний

Рекомендуемая мера: Разработать и внедрить адаптер (Anti-Corruption Layer). Начать с эмуляции старого OLE-интерфейса для обратной совместимости, с постепенным переходом клиентов на новый REST API.

## 3. Обратная совместимость с существующими системами (1С, ККМ)

Приоритет: Высокий

Рекомендуемая мера: Создать адаптеры-прокси, которые будут обеспечивать совместимость API. Использовать feature flags для постепенного перевода клиентов на новый функционал.




# Инфраструктура

## 1. Отсутствие отказоустойчивости

Приоритет: Высокий

Рекомендуемая мера: Спроектировать инфраструктуру с учетом отказоустойчивости: минимум 2 ноды для каждого сервиса в K8s, Health Checks.

## 2. Недостаточные ресурсы серверов для обработки возросшей нагрузки

Приоритет: Средний

Рекомендуемая мера: Провести нагрузочное тестирование пилотного сервиса на реалистичных данных и сценариях (x5 нагрузка). На основе результатов — заложить ресурсы в проект инфраструктуры.

## 3. Сложности миграции данных с физического сервера

Приоритет: Средний

Рекомендуемая мера: Разработать поэтапный план миграции данных: сначала исторические/архивные данные, затем операционные. Использовать инкрементальную миграцию.




# Персонал

## 1. Недостаток квалификации у текущих IT-специалистов

Приоритет: Высокий

Рекомендуемая мера: Привлечь внешнего архитектора на ключевые этапы проектирования и запуска. Начать обучение команды (Kubernetes, микросервисы, DevOps) параллельно с проектом.

## 2. Отсутствие DevOps-культуры для микросервисов

Приоритет: Средний

Рекомендуемая мера: Назначить ответственного за DevOps-практики. Внедрить Infrastructure as Code, централизованное логирование и мониторинг (ELK, Prometheus) с первого сервиса.

## 3. Сопротивление изменениям со стороны медицинского персонала

Приоритет: Низкий

Рекомендуемая мера: Jбучить 1-2 сотрудника, которые будут помогать коллегам. Регулярно собирать фидбэк.




# Процессы

## 1. Отсутствие плана отката при неудачной миграции

Приоритет: Критический

Рекомендуемая мера: Немедленно разработать и утвердить детальный план отката для каждого этапа миграции, включая процедуры возврата к legacy-системам и восстановления данных.

## 2. Отсутствие автоматизированного тестирования

Приоритет: Высокий

Рекомендуемая мера: Внедрить CI/CD pipeline с обязательным набором тестов (unit, integration, API) для каждого нового сервиса. Без green pipeline — запрет на деплой в staging.

## 3. Неформализованные процессы обработки данных

Приоритет: Высокий

Рекомендуемая мера: Еще раз провести оценку, как происходит движение данных в системе и актуализировать диаграммы потоков данных. 

## 4. Отсутствие документации текущих бизнес-процессов

Приоритет: Низкий

Рекомендуемая мера: Создать репозиторий документации и начать фиксировать текущие процессы по мере их анализа в рамках миграции. Использовать wiki-систему, например Confluence
